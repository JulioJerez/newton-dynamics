02 — foundation

ndModelArticulation

The generic skeleton framework underneath everything. It knows nothing about wheels or engines — only that a physical object can be represented as a tree of rigid bodies connected by joints, with the odd extra joint that breaks the tree shape entirely.

The core data shape

An ndNode pairs one body with the joint that attaches it to its parent. m_rootNode is the top of the tree (a chassis, a torso, a robot base). Some joints don't fit a tree at all — a gearbox links two branches that are already connected elsewhere — so those go in a side list, m_closeLoops, instead of being forced into parent/child form.

NodeIterator — the workhorse

A templated method in the header that walks the whole tree with an explicit stack (no recursion, so it can't blow up on deep hierarchies) and calls a lambda on every node, then does the same for the loop joints. Nearly every operation elsewhere in the vehicle code — applying forces, disabling joints, cloning a skeleton — is written as a small lambda handed to this one function. 

template <typename Function>
void ndModelArticulation::NodeIterator(Function func)
{
    // walks m_rootNode's tree with a stack, then every close-loop node
}

What else lives here

  • CalculateCentreOfMassKinematics / …Dynamics — aggregate the whole structure's mass, momentum, and inertia into one virtual point, borrowing the same math used to derive the Zero Moment Point in bipedal-robot walking research.
  • Serialize / Deserialize — convert the tree to and from ndMesh, so a model can be saved to disk and reloaded.
  • IsSleeping / SetSleep — lets an entire articulated structure go dormant together rather than each body deciding independently.
Why this layer exists

Vehicles, ragdolls, and robot arms are all "trees of bodies with one or two extra constraints." By solving that problem once, generically, the vehicle classes below only have to add vehicle meaning on top — not tree-walking logic.

03 — vehicle physics

ndMultiBodyVehicle

Inherits the tree machinery above and gives it a steering wheel. This is where "chassis," "tire," "motor," and "differential" become real concepts, and where tire friction is actually computed.

Assembling a vehicle

AddChassis, AddTire, AddMotor, AddDifferential attach parts directly to the chassis as tree limbs. AddGearBox, AddTorsionBar, and AddDifferentialAxle instead register as loop joints, since a gearbox connects a motor branch to a differential branch that are already both attached to the chassis elsewhere in the tree.

Two tire-friction models, side by side

CoulombTireModel is the simple case: a flat static/dynamic friction coefficient, reduced a bit under braking.

PacejkaTireModel implements the "Magic Formula" from tire dynamics literature — friction as a function of slip angle and slip ratio, combining lateral and longitudinal force. The code comments are unusually candid about this one: the author documents two textbook methods for combining slip, notes the book itself calls the implemented method "incorrect," and explains why it was kept anyway (it's stable in practice; the alternative never produced realistic results).

Per-frame update order

Update() runs, in sequence:

  • ApplyAerodynamics — speed-dependent downforce, read from a small lookup table (ndDownForce) rather than a closed-form drag equation.
  • ApplyTireModel — filters contacts to the tire's actual contact patch, then dispatches each contact point to Coulomb or Pacejka based on the tire's configured friction model.

PostUpdate() then calls ApplyAlignmentAndBalancing, which gently corrects tire velocity/angular velocity toward what the chassis implies, preventing small numerical drift from accumulating.

CalculateRestSprungWeight — solving for who's carrying what

Before the Pacejka model can scale forces by load, the engine needs to know each tire's static share of the vehicle's weight. This method builds a small constrained linear system by hand (Jacobians, a mass matrix, Cholesky factorization) and solves it once, at rest, to get a per-tire "sprung weight" — a miniature physics solve nested inside the vehicle setup code.

04 — alternate wheel model

ndConvexCastVehicle

Same vehicle concept, different physical wheel. Instead of letting a spinning wheel-shaped rigid body collide with the ground the normal way — which is fast but prone to jitter and tunneling — this variant sweeps a shape downward every frame and builds the contact by hand.

Why not just use a normal wheel body?

A thin, fast-spinning collision shape sitting right at the suspension's contact point is a classic source of instability: high angular velocity plus a small shape can tunnel through thin ground geometry or jitter under load. Sweeping a convex shape from the top of suspension travel down to the bottom, and treating the sweep result as the contact, sidesteps that instability at the cost of doing the contact generation manually.

CalculateConveCastTireContacts — the manual contact pipeline

  • Deactivates the tire's existing contacts.
  • Casts the wheel shape from its upper suspension-travel position downward by the suspension's full range.
  • Recovers penetration depth from the suspension's own known position — a convex cast reports zero penetration by construction, so penetration has to be derived from where the wheel actually sits, or the tire will slowly sink into whatever it's resting on.
  • Sorts and groups the resulting contact points by which body they hit, then builds up to two real ndContact joints per tire from those groups.

ConvertToMotorVehicle — a private drivetrain solver

This override does everything the base class does, then goes further: it clones the vehicle's skeleton into a private ndSkeletonContainer, and deactivates the tires, motor, and differential joints from the main world solver. The drivetrain is no longer solved by the engine's global physics step — it's solved separately.

Update — a solve sandwiched inside a solve

Each frame, this class:

  • Refreshes tire contacts via the convex-cast pipeline above.
  • Temporarily swaps every body's skeleton pointer to the private, cloned skeleton.
  • Runs its own embedded ndIkSolver (m_solver) — SolverBegin → Solve → SolverEnd — in isolation from the rest of the world.
  • Restores each body's original skeleton and integrates drivetrain parts (tires, motor, differential) directly, while chassis-adjacent "structural" parts are left for the main solver to finish integrating.

A small sleep counter (m_sleepCounter) skips this entire pipeline once the vehicle has been at rest for eight consecutive frames — the convex-cast sweep isn't free, so an idle car shouldn't keep paying for it.

05 — side by side

ndMultiBodyVehicle vs. ndConvexCastVehicle

Aspect ndMultiBodyVehicle ndConvexCastVehicle
Wheel–ground contact Ordinary rigid-body collision detection on the wheel shape. Manual convex-cast sweep each frame; contacts built by hand.
Drivetrain solve Solved together with the rest of the world, in the main step. Solved separately with a private, cloned skeleton and an embedded ndIkSolver.
Best suited for Higher-fidelity simulation where true wheel collision matters. Fast, stable arcade/game-style driving where jitter and tunneling must be avoided.
Sleep handling Delegated to the generic ndModelArticulation::IsSleeping. Adds its own frame-counted sleep gate around the extra convex-cast cost.
