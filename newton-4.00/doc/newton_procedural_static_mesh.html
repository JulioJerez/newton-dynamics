Procedural Static Mesh Collision

The ndShapeStaticProceduralMesh interface provides a way for an application to supply dynamically generated static collision geometry without having to construct Newton's internal collision representation itself.

Procedural Mesh Input Is a Standard Indexed Mesh

The application supplies a patch as a conventional indexed polygon mesh: a vertex array and an index array describing the faces.

For example, a quad can be supplied as two triangles:

{0, 1, 2}
{2, 1, 3}

The application does not need to explicitly provide the adjacency information required by the collision system.

This is an important difference from the older Newton mesh interface. In previous versions, the application was responsible for providing a much more complete collision-mesh description, including explicit face adjacency and additional collision information. That information is now generated by Newton from the ordinary indexed mesh.

Connectivity Is Derived From the Index Buffer

Connectivity is still important to Newton's collision algorithms, but it is implicit in the indexed mesh supplied by the application.

For example, in the following mesh the two triangles share the edge (1, 2): 

{0, 1, 2}
{2, 1, 3}

Newton's ndPatchMesh::GetFacesPatch() function discovers this relationship by processing the edges of the indexed faces. It constructs the collision-specific connectivity internally rather than requiring the application to provide a neighboring-face array.

This allows Newton to retain the geometric information needed by its contact-generation algorithms while presenting the application with a much simpler interface.

Optional Mesh Conditioning

Newton can also use the supplied geometry to improve the triangulation of procedural surfaces.

For example, consider a planar quad represented by: 

{0, 1, 2}
{2, 1, 3}

The internal preprocessing can evaluate the diagonal using geometric criteria such as the Delaunay circumcircle test and, when appropriate, change the diagonal to: 

{0, 1, 3}
{3, 1, 2}

This is particularly useful for procedural geometry generated naturally as quads or other polygons. The application can provide the geometry in the form most convenient for its generator while Newton performs the collision-specific preprocessing.

Newton also provides low-level computational-geometry functionality that an application can use if it wants to perform similar processing itself. However, this is not required to use the procedural mesh interface.

The Procedural Mesh Does Not Sacrifice Collision Quality

Important: A procedural mesh is not a lower-quality collision representation. The same low-level collision algorithms are used for the actual contact generation.

The important distinction is where preprocessing takes place.

A conventional collision tree can perform substantial preprocessing when the collision shape is built. This preprocessing can optimize the geometry, including triangulation, vertex processing, connectivity, and other information used during contact generation. That approach works well for geometry that is relatively static.

For continuously generated or modified geometry, rebuilding such a fully optimized collision structure every time the geometry changes would defeat much of the advantage of procedural geometry.

The procedural interface therefore allows the application to supply the current indexed mesh directly. Newton performs the necessary patch-level processing and then uses the same underlying collision algorithms used for collision geometry obtained through its other mesh representations.

Therefore, a procedural mesh does not inherently mean that Newton uses a simpler collision algorithm. It means that the geometry can be provided dynamically while Newton derives the collision-specific information from the supplied mesh.

A prebuilt collision tree may be able to report fewer faces during a query because it has additional preprocessing and convex optimizations available to it. This is a performance optimization for a reusable static representation, not a fundamental difference in contact quality.

What the Application Actually Has to Do

For a procedural surface such as terrain, a road generated from a spline, a voxel-derived surface, a procedural planet, or a dynamically generated environment, the application can follow a simple model:

  1. Determine which portion of the procedural surface overlaps the requested AABB.
  2. Generate the corresponding vertices.
  3. Generate the indexed faces.
  4. Return the patch to Newton.

Everything else required by the collision system can be derived internally.

In particular, the application does not need to construct a second collision-specific hierarchy merely because the geometry is procedural.

Summary

The key idea is:

The application supplies an indexed mesh. Newton derives the collision connectivity, conditioning, and other collision-specific information from that mesh.

This makes the procedural interface much closer to a conventional graphics mesh interface than the older Newton collision-mesh interface, while still allowing Newton's collision system to operate on the geometric information it needs for high-quality contact generation.
